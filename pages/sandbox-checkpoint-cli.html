Investigation · 2026-11-14 · from the #C0BUF5V2S83 thread

Saving a checkpoint from inside a cloud box

Avi tried to save a checkpoint on a box and could not. The guess in the thread was that the box ships an old CLI. That is not the cause. The box runs current code. The checkpoint command is blocked inside a box on purpose, in two places.

1. The box CLI is not stale. Boxes get a superset binary built from main by the nightly sandbox release. This box has superset-2.0.8 and host-service-2.0.8+65dea8b3 (main as of 2026-11-13 17:57 PT). Updating the sandbox would change nothing.

2. Checkpoint save is in the CLI, but hidden in a box. The command is superset environments replace <env> --workspace <ws>. It is tagged sandbox: false, so in a box it prints Unknown command: replace. The API also refuses environment.promote from a box credential.

3. The real bug is new. #9707 (merged 2026-11-13) added "Set up Environment" in a cloud chat. It runs the superset:environment skill inside the box. Step 5 of that skill is the checkpoint command, which cannot work there.

1. Which CLI the box ships, and where it is set

Checked on this box (SUPERSET_SANDBOX_WORKSPACE_ID=65bbe9f8…, image tag env-internal-mwfrhk47):

The committed rows are only a floor for PR boot tests. The real versions are set at release time:

  • packages/sandbox/src/assets/produce.ts:405: cli() builds packages/cli from the release checkout. It names the file with the version in packages/cli/package.json, so the label stays 2.0.8 even when the code is newer than the cli-v2.0.8 tag.
  • .github/workflows/sandbox.yml:17: production-release runs bun run release --production from main every night at 09:00 UTC, and on merges that touch packages/sandbox/**.
  • packages/sandbox/bundle/steps/install-cli.sh links that binary to /usr/local/bin/superset and paradev on every boot.

Note: the version label cannot tell you how fresh a box CLI is. The host-service suffix (+65dea8b3) is the commit to check. That build already includes #9707 and the replace command.

2. Is checkpoint save in the CLI?

Yes, since #7913 (2026-09). Two commands call environment.promote:

  • superset environments replace <env-id> --workspace <ws-id> --yes: saves a checkpoint into an existing environment. This is the same call as the desktop "Save checkpoint" menu item (SaveCheckpointDialog.tsx).
  • superset environments save --workspace <ws-id> --name <name>: saves the box as a new environment.

Both work from a laptop. Inside a box they are blocked twice:

  1. The CLI hides them. packages/cli/src/commands/environments/replace/command.ts:10 sets sandbox: false. packages/cli/cli.config.ts:35 treats any process with SUPERSET_SANDBOX_WORKSPACE_ID as a box, and packages/cli-framework/src/router.ts:43 removes those commands from the tree. Added in #7794: "visibility only; the API keeps enforcing". Verified here: superset environments --help lists only list and secrets.
  2. The API refuses them. A box calls the API with the box credential. packages/trpc/src/trpc.ts:127 rejects any path that is not in SANDBOX_ALLOWED_PROCEDURES (packages/trpc/src/lib/sandbox/api-credential.ts:25). That list has environment.get, list and secrets.list, but not environment.promote.

3. Why this showed up now

The superset:environment skill was written to run on the user's machine (plugins/superset/skills/environment/SKILL.md:10: "You run on the user's machine with their Paradev login. You build the environment by driving a cloud box from here.").

#9707 added a "Set up Environment" chip to cloud chats and the new-workspace screen. Its prompt (apps/desktop/src/renderer/routes/_authenticated/utils/environmentSetupPrompt/environmentSetupPrompt.ts:8) says: "You are already in a box on that environment, so set it up here instead of starting another box." So the agent runs the skill inside the box. Steps 1–4 work. Step 5 (environments replace) cannot. #9707 is not in the cli-v2.0.8 / desktop 2.0.8 tag, but it is in the box build, and anyone on canary or dev hits it.

4. Why this is not a one-line fix

Removing sandbox: false and adding environment.promote to the allowlist would let the call through, but the box would kill its own caller:

  • promoteSandboxToEnvironment (packages/trpc/src/lib/sandbox/vercel.ts:571) runs source.snapshot(), which stops the box. The CLI process waiting for the reply, the agent that ran it, and its terminal all stop. The request takes about 50 s, and the client is gone before the reply. Then runBoot starts the box again.
  • The box credential acts as the creator but anything in the box can use it (comment on sandboxProcedure). If promote into an organization-scoped environment were allowed, code in one box could replace the golden that every new workspace forks from. The allowlist leaves it out on purpose.

So I did not open a PR.

Options

A. Hand the checkpoint back to the person · recommended now

Change step 5 of the skill: when SUPERSET_SANDBOX_WORKSPACE_ID is set, the agent stops and asks the user to click … → Save checkpoint on the workspace (added in #9707), or to run superset environments replace from their laptop. Also fix line 10 of the skill so it covers both places it runs. This is a skill change and a superset plugins publish superset --bump patch, with no API change. Small, but it changes the setup flow, so the owner of #9707 should agree first.

B. Let a box ask for its own checkpoint, done after the reply

Add a sandbox procedure such as environment.requestCheckpoint to SANDBOX_ALLOWED_PROCEDURES. It accepts only the caller's own workspace (ctx.sandboxWorkspace.id) and only that workspace's own environment, and only when the environment is personal and owned by the creator. It returns at once and runs the promote in the background (a job, not inside the request). Then show environments replace in a box again, routed to this procedure, with a message that the box restarts now. The chat on the box must resume after the restart, so check that chat sessions survive a stop and wake. This needs a trpc-compat review and a host-service/sandbox release.

C. Run the setup agent outside the box

Make the chip start the setup in a local chat that drives the box, as the skill was written for. This works with no API change, but it undoes the in-box setup that #9707 added and needs a local host.
