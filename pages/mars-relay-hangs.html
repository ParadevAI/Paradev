Mars host: intermittent relay "Request timed out"

Host e89c80f0047616c8e1a3bf4b1791dd8d, org 7b3ff211-…2400, host-service 2.0.5. Seven workspace.create calls failed after about 66–68 s in two windows on 2026-11-10 (17:55:53–17:59:03 and 18:10:00–18:11:19 UTC). workspace.list and terminal list also stalled. The control tunnel stayed connected for the whole time. This is a read-only investigation. No code was changed.

Most likely cause: the relay does not notice when the per-request dial-back socket closes before the response comes back. If that socket drops with a 1006 during an exchange, nothing fails the request. The relay waits for the full 65 s exchange timeout, then answers "Request timed out" because the control socket is still up. A network blip that lasts less than a second becomes a 65 s hang. The customer's repeated 1006 closes with quick reconnects match this. Control-socket health does not protect against it, because each request uses its own new socket.

Evidence

1. Only one code path makes this exact error, and its timing matches

  • "Request timed out" appears only at apps/relay/src/index.ts:377-385. The relay returns it only when the HTTP exchange failed with reason: "timeout" and isConnected() says the host control socket is open. This is consistent with "control stayed connected".
  • The exchange timeout is EXCHANGE_TIMEOUT_MS = DIAL_TIMEOUT_MS + 30_000 (apps/relay/src/http-exchange.ts:7). DIAL_TIMEOUT_MS = RELAY_CONNECT_TIMEOUT_MS + 5_000 = 35 s (packages/shared/src/tunnel-protocol.ts:98-101). So the timeout is 65 s. Add JWT verification, the access check and the extra isConnected round trip, and you get the observed 66–68 s.
  • So the relay received neither http:end nor stream:dial-failed for that ticket in 65 s.

2. The failed creates never finished on the host (PostHog)

Slow host-side work is therefore not the main suspect. List queries stalled in the same windows, so the failure is in the request path, not in one procedure.

3. A dial socket that closes during an exchange is ignored on both ends

Each relayed tRPC HTTP call is one kind:"http" dial. The relay sends stream:dial over control. The host opens a new WebSocket to /v2/dial. The relay pushes the request frames on that socket, and the host answers on the same socket.

  • Relay: HostTunnel.handleGone() (apps/relay/src/host-tunnel.ts:348-382) handles a closing dial socket by clearing early frames and timers and closing a peer, if one exists (lines 372-381). It never calls httpExchanges.fail(ticket). Pending exchanges are settled only by the 65 s timer, a host-sent stream:dial-failed, or abortAll() when the control socket goes (line 364). No test covers "dial closes mid-exchange" (apps/relay/src/http-exchange.test.ts covers slow dial, expiry, dial-failed, completion and shutdown only).
  • Host: serveHttpDial() (packages/host-service/src/tunnel/tunnel-client.ts:332-363) sets onmessage and onerror but no onclose. After the socket opens, nothing reports a lost exchange or retries it. forwardHttp() (lines 365-429) sends fetch to localhost with no abort signal. If the socket dies while the handler runs, the response goes to a closed socket and is lost without an error. This code is the same in 2.0.5 and on main.
client ──HTTP──▶ Worker ──RPC proxyHttp──▶ HostTunnel DO (exchange timer 65 s starts) DO ──control: stream:dial{ticket,kind:http}──▶ host ✓ control is healthy host ──new WS /v2/dial?ticket──▶ edge ─▶ Worker ─▶ DO ✓ onDialConnect sends http:request + http:end ✗ dial socket drops (1006): network, edge or Worker↔DO hop DO.handleGone(dial) → exchange not failed host (no onclose) → no dial-failed, no retry, handler never runs …65 s… timer → reason "timeout" → isConnected()=true → 502 "Request timed out"

4. Why control survives while requests fail

The control socket is one long-lived connection. Each request opens a fresh TCP+TLS+WS connection from the GCP VM through Cloud NAT to Cloudflare anycast. That connection can land on a different edge colo than control, and from there it crosses a Worker→DO hop to the host's Durable Object. A path problem that affects only new connections, or only the edge→DO leg, hits every request in a window and leaves control alone. This also fits "retries minutes later work". We cannot yet say which hop drops the sockets. That needs the logs below.

Proposed fix

  1. Relay: fail or retry an exchange when its dial socket goes away. In handleGone, when state.kind === "dial" and httpExchanges.has(state.ticket), settle the exchange right away. Give it a distinct reason (for example "stream-lost") and map it to BAD_GATEWAY "Connection to host dropped". This turns a 65 s hang into a fast, retryable error. Add the regression test "dial closes before http:end".
  2. Make it safe to re-dial automatically. Have the host send an http:accepted frame right before it calls fetch locally. If the dial drops before that frame, the handler never ran, so the DO can re-dial once with a new ticket, even for mutations. If it drops after, surface the error and do not replay a non-idempotent call.
  3. Host: watch the dial socket after it opens. Add onclose in serveHttpDial and abort the local fetch through an AbortController. If the socket closes before http:end arrives, send stream:dial-failed over control. Old relays treat that frame the same way.
  4. Split the timeout. Allow one deadline for "request delivered/accepted" (about 35 s) and a separate one for the handler. A host that has accepted a long create should not share a budget with a dial that never landed.
  5. Correlation logging (cheap, ship first). Log the ticket on both legs. Relay: dial sent, dial connected, dial closed (code, ms since open), exchange outcome and duration. Host: dial received, dial open/fail (attempt n), http:end received, local fetch status and ms, dial closed (code). Today 2.0.5 logs nothing when it receives a dial, so we cannot tell these cases apart from host logs.
  6. Ask the customer to upgrade host-service to ≥ 2.0.6. That release includes #9514, which retries the Node 22 handshake failure and closes the relay stream on a local socket error.
  7. Small fix: apps/mobile/hooks/useDeleteWorkspace/useDeleteWorkspace.ts:147 still says "30s exchange cap". The cap is 65 s.
