Thin sandbox: PR plans

Ten changes that shrink what a cloud workspace box carries: less in the image, nothing on disk at stop that should not be there, and the large per-workspace data moved off the box. The goal of this pass is a smaller sandbox that customers can still rely on. Boot time is the expected payoff and is measured as a separate step. Sizes are from the inventory page, measured 2026-11-16.

Image

1. Drop staged archives after their step consumes them

Saves ~0.55 GBSize mediumRisk boot re-downloads if wrongFiles bundle/setup, bundle/steps/*.sh, manifest.ts

sync-assets keeps the codex tar, the Chrome deb, the host-service tar and the pdev tar in media/ after they are unpacked. It skips a download only when the file exists and its .hash sidecar matches. Make the sidecar sufficient for archives a step consumes, and let the step delete the archive when it succeeds. The claude and superset binaries run in place and stay.

# manifest.ts: each asset row gains consume = true | false
#   true:  chrome .deb, codex .tar.gz, host-service .tar.gz, pdev .tar.gz, theme tars
#   false: claude, superset (executed from media/), fonts, icons

# setup: sync_assets, per row
if consume and read(dest.hash) == hash and not exists(dest):
    exit 0                      # installed and discarded; nothing to fetch
if exists(dest) and read(dest.hash) == hash:
    exit 0
download, verify sha256, install, write dest.hash

# setup: run-step, after a step exits 0
for row in assets where row.step == step and row.consume:
    rm -f row.dest              # keep row.dest.hash

# a step whose version marker moved but whose archive is gone
if step.marker != step.version and any consumed archive missing:
    rm its .hash; sync that row; then run the step

# prune_media: also drop orphan .hash files the manifest no longer names

Test: boot-twice gains two expectations. After the first boot no consumed archive is on disk. The second boot fetches nothing. Then bump one step's version in a test bundle and confirm exactly that archive is re-fetched.

3. Remove emacs and Go dropped

Decided 2026-11-16: keep both. The base box exists to put as few bottlenecks as possible in front of a customer onboarding a repo. Go is a mainstream toolchain and a missing one is a hard stop. Emacs is 150 MB and SUPER-2261 lists it. The 0.43 GB is not worth it.

4. JDK, ffmpeg and ImageMagick opt-in dropped

Decided 2026-11-16: keep all three. ImageMagick's import is the only real screenshot tool on the Linux desktop (there is no scrot or xfce screenshooter), and agents use it to crop and stitch images. ffmpeg is the only way to record the screen or build a video from frames. Both are core to how an agent shows its work. The JDK (Java runtime and compiler) is needed by Java, Kotlin and Android projects and by tools such as Gradle and Maestro.

The rule this sets: the image carries what a meaningful share of repos need to start. We cut only what nobody can notice.

Swap

6. No swap in any snapshot the API takes

Saves 2 to 16 GB per affected snapshotSize smallRisk lowFiles packages/trpc/src/lib/sandbox/vercel.ts

memguard grows 2 GB swapfiles under /var/swap and deletes them only at the next boot. Any stop in between snapshots them. This PR covers the stops our API performs: promote, archive, the meter, the reaper and the wake restart. The box measured today held 8 GB.

// vercel.ts
const INHERITED_IDENTITY = [
    ...,
+   "/var/swap",                    // a golden must not carry the source box's swap
]

async function releaseSwap(sandbox):
    // best effort, bounded: a box that cannot page back in is about to stop anyway
    await sandbox.runCommand({ sudo: true, cmd: "bash", args: ["-c", `
        kill "$(cat /run/superset/memguard.pid)" 2>/dev/null      # or it grows swap again
        for f in /var/swap/superset-*; do
            timeout 20 swapoff "$f" 2>/dev/null
            rm -f "$f"                                            # unlinked even if still in use
        done
    `] }).catch(log)

export async function stopSandbox(id):
    sandbox = await getSandbox(id)
    if sandbox.status == "running":
+       await releaseSwap(sandbox)
        await sandbox.stop()

export async function stopAndSnapshot(name):
+   if sandbox.status == "running": await releaseSwap(sandbox)
    await sandbox.stop(); await waitForStopSnapshot(...)

promoteSandboxToEnvironment:
+   await releaseSwap(source)       // before source.snapshot()
    // the strip list covers the case where release timed out

Call sites need no change: meter.ts (three), reap.ts (two), cloud-workspace.ts and wake.ts all go through the two functions.

Open point: rm of a swapfile still in use frees its blocks only when the kernel releases it at shutdown. Whether Vercel's snapshot then skips those blocks depends on their snapshotter, since this disk has no discard. PR 0's inventory shows the answer: snapshot a box before and after this change.

Docs: correct the memguard entry in docs/cloud-sandbox-considerations.md and add a mismatches entry: a stop snapshots everything on disk at that moment.

7. No swap at the idle stop

Saves the same, for the common caseSize mediumRisk reaps user processes minutes before the stopFiles superset-memguard, sandbox-expiry.ts, a bundle release

Most stops are the platform's idle timeout, and the API only observes them afterwards. The box does not know when its session ends. The API does, every time it records the box awake, so it tells the box and memguard drains swap as the deadline approaches.

// sandbox-expiry.ts: recordSandboxAwake(row, { expiresAt, sessionId })
+ await writeFile(sandbox, "/run/superset/expires-at", String(expiresAt.getTime()))
  // fire and forget; a box on an older bundle ignores the file

# superset-memguard, in the main loop
DRAIN_BEFORE_S=180
expires_ms = read /run/superset/expires-at or 0
if expires_ms > 0 and now_ms > expires_ms - DRAIN_BEFORE_S*1000:
    draining = 1
else:
    draining = 0                    # an extend moved the deadline: back to normal

if draining:
    skip grow_swap
    for f in swap_files (newest first):
        if swap_used_in(f) + floor < mem_avail:
            swapoff f; rm f; log "swap.drain f"
        else:
            victim = victim_at_or_above 500 || victim_at_or_above 0   # user processes only,
            kill -9 victim; log "drain.reap ..."                      # never host-service or desktop
            break                    # re-evaluate next tick

Why reaping is acceptable: the session ends in under three minutes and takes every process with it. An extend inside that window, from a user returning, cancels the drain, so the only loss is a dev server that the start hook brings back.

Test: a bun test of the drain decision as a pure function of (expires, now, mem, swap). On a real box: fill swap, set a short timeout, confirm /var/swap is empty before the stop and the next snapshot's sizeBytes dropped.

Drives

9. Drive spike

Size one script, one docRisk none, no product codeFiles packages/sandbox/src/drive-spike.ts, plans/

Three questions decide PRs 10 and 12 and the docs answer none of them: what a cold read costs over 213k small files, whether a forked drive is copy-on-write and shares its parent's cache, and whether the mount supports file watching.

base = await Drive.getOrCreate({ name: "spike-base", region: "sfo1" })
writer = await Sandbox.fork({ sourceSandbox: GOLDEN, mounts: { "/mnt/ws": base } })
run(writer, "git clone --depth 1 $REPO /mnt/ws/repo && cd /mnt/ws/repo && BUN_INSTALL_CACHE_DIR=/mnt/ws/.bun-cache bun install")
await writer.stop()

t = time(() => fork = await base.fork({ name: "spike-fork" }))          // copy or copy-on-write?
box = await Sandbox.fork({ sourceSandbox: GOLDEN, mounts: { "/workspace": fork } })

record(box, "findmnt -no FSTYPE,SOURCE /workspace")                      // block device or FUSE?
record(box, "inotifywait probe: touch a file, expect an event")
for label in ["cold", "warm"]:
    record(box, time("git -C /workspace/repo status"))
    record(box, time("bun run typecheck --filter=@superset/trpc"))
    record(box, time("find /workspace/repo/node_modules -type f | xargs cat > /dev/null"))   // worst case
// stop, resume, repeat "cold" to see what a wake on a new host costs
// second fork, second box, same timings: does the parent's cache serve a sibling?

// tools drive, for PR 12
tools = Drive.getOrCreate({ name: "spike-tools" }); write claude + codex into it; stop
box2 = Sandbox.fork({ sourceSandbox: GOLDEN, mounts: { "/opt/agents": tools.snapshot() } })
record(box2, time("/opt/agents/claude --version")) cold, then warm

Pass bar, proposed: the mount is a real filesystem with inotify, a drive fork takes seconds, and cold git status plus typecheck is within two times warm. If cold is worse but bounded, a background readahead at boot is the mitigation and gets measured in the same script.

Also send to Vercel: are sandbox fork snapshots deltas over the parent; is a drive fork copy-on-write with a shared cache; and is a shared read-only drive snapshot the intended way to ship platform tools to every sandbox, with a cache shared across hosts or per host.

10. Repo and workspace state on a per-workspace drive

Saves ~7 GB per workspace snapshot, more with build outputSize large, five PRsRisk high, changes the lifecyclegated on 9

One drive per workspace, forked from the environment's golden drive. It holds the repo, its dependencies and the user's home state. The sandbox keeps only the image and tools. A plan document comes first. The sequence:

// 10a. Schema + lifecycle
cloud_workspaces.provider_drive_id        environments.golden_drive_id
provision:  drive = goldenDrive.fork({ name: "ws-" + id })
delete:     await drive.delete()          // after the sandbox is gone; a drive attached to a running box cannot be deleted

// 10b. Mount
provisionSandbox / wakeSandbox:
    Sandbox.fork({ sourceSandbox: golden, mounts: { "/data": drive }, ... })
    // mounts are fixed per session and not inherited by forks: pass them on every create and wake

// 10c. Layout on the box (superset-boot)
/data/workspace   -> bind or symlink to /workspace
/data/home        -> ~/.bun  ~/.cache  ~/.config  ~/.claude  ~/.codex  ~/.npm  ~/.local  shell history
managed env:  BUN_INSTALL_CACHE_DIR=/data/home/.bun/install/cache   // same filesystem as node_modules, hardlinks survive
              NPM_CONFIG_PREFIX=/data/home/.npm-global  PIPX_HOME  CARGO_HOME  GOPATH

// 10d. Promote
promoteSandboxToEnvironment:
    stop source; goldenDrive = sourceDrive.fork({ name: "env-" + id })
    strip identity paths that now live on the drive from goldenDrive (mount it once, rm, stop)

// 10e. State machine
the single read-write mount means: wake must wait for the previous session to release the drive
update the sleep model and run .agents/skills/verify-sandbox-asleep
existing workspaces: migrate on next wake (rsync /workspace and home into a new drive) or leave on-box until archived

Follow-on, not in this PR: once the drive holds all state, a wake can fork the golden fresh and drop the per-workspace sandbox snapshot. That is the boot-time step and is deliberately separate.

Agents

11. Per-environment agent config moved out

Decided 2026-11-16: not part of this work. With the shared tools drive in PR 12, every agent reaches every box at no cost, so a setting is not needed to keep the box thin. Credentials are already brokered per user, only for providers that user has connected. The setting remains a good product feature for org policy (offer only one vendor's agent) and a shorter picker, and gets its own ticket.

It comes back into scope if the spike fails and agents are installed into each environment's snapshot. Then each enabled agent costs disk and the setting is how a customer controls that.

12. Agent CLIs off the image, onto a shared tools drive

Saves ~1.1 GB of image; an agent release no longer grows every workspaceSize mediumRisk mediumgated on 9

claude is a 280 MB binary, codex 475 MB unpacked, pdev 104 MB. Three ways to deliver them:

RouteNew workspaceExisting workspaceCost
Download on boot (today, same flow as Chrome)in the imagedownloads each release at next boot, before host-service startsevery release is written to every workspace's own disk and snapshot
Bake into the environment's snapshotinherits from the goldennever sees the golden again; still needs the boot downloadre-snapshot every environment on every agent release
Shared read-only drivemountedmounted at next wakeone write per release; one of four mount slots; cold first launch unknown

One drive holds every agent. A box links whatever the manifest lists, so adding an agent to the platform is a release-side change. Reads are lazy, so an agent nobody launches costs a box nothing.

// release.ts
tools = await Drive.getOrCreate({ name: "agent-tools", region })
builder = await Sandbox.create({ mounts: { "/opt/agents": tools } })       // the single read-write mount
for agent in assets where kind == "agent":                                  // claude, codex, pdev, later others
    dir = /opt/agents/{agent.name}/{agent.sha}

await builder.stop()

// vercel.ts: provisionSandbox, wakeSandbox
mounts["/opt/agents"] = tools.snapshot()          // point in time; fixed for the session

// superset-boot

    ln -sfn /opt/agents/{entry.name}/{entry.sha}/{entry.bin} /usr/local/bin/{entry.name}
if manifest missing: stamp "agents.unavailable"; continue      // fail open: the box still boots

// image
remove claude, codex, pdev rows from assets.json; delete steps/install-agent-clis.sh

// regions: a drive lives in one region and must match the sandbox's. One tools drive per region we run in.

Fallback if the spike fails: install agents into each environment's golden and keep the boot download for updates. The image still stops carrying them. PR 11 returns to scope.

Agents a user installs themselves go on the workspace's own drive with the rest of their state, not here.
