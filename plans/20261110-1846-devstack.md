# devstack: a Paradev-native sprint plugin

This plan is a living document. Keep `Progress`, `Surprises & Discoveries`, `Decision Log` and
`Outcomes & Retrospective` current as work proceeds. It follows the plan format that the
`devstack:plan` skill writes, so it is also the first dogfood of that format.

Research: https://app.superset.sh/page/devstack-a-superset-native-gstack-research-qjfbzo

## Purpose / Big Picture

gstack (github.com/garrytan/gstack) turns one Claude Code session into a serial sprint of
opinionated roles. Paradev already has what gstack builds by hand: parallel workspaces, an agent
launcher, a skills marketplace, automations, pages, and an MCP proxy for Linear, GitHub and Sentry.
What it lacks is an opinionated end-to-end workflow that tells an agent "here is the sprint, run
these in order".

devstack is that workflow, shipped as a skills-only first-party plugin in `plugins/devstack/`.
After it is installed (`superset plugins install devstack`), a user in any repository can say
"plan this", get a plan split into independent work units, fan those out to parallel agents in
isolated workspaces, get an independent review from a different agent, and ship a PR. A weekly
automation publishes a retro page.

The sprint is Frame → Plan → Fan-out → Review → Verify → Ship → Watch → Retro. Every skill reads
and writes a small artifact and ends by naming the next skill.

## Context and Orientation

A *plugin* is a directory `plugins/<name>/` with a `plugin.json` manifest and `skills/*/SKILL.md`
files. It ships no code. `.agent-marketplace.json` at the repo root lists first-party plugins;
`superset plugins publish <name>` records a version there and regenerates
`packages/shared/src/plugins/manifests.generated.ts` (never hand-edit it). Merging to main tags
`<name>@<version>`, and that tag is what a machine installs. `bun run check:plugins` is the CI
gate. Full details: `docs/plugins.md`.

A *skill* is a markdown file with `name` and `description` frontmatter. The description is the
only thing an agent sees when it decides to load the skill. Installed skills land in
`~/.agents/skills/<plugin>-<skill>` and, for Claude, `~/.claude/skills` as `<plugin>:<skill>`.

The `superset` plugin (`plugins/superset/`) is different: it is a managed source bundled with the
desktop app and CLI (`packages/agent-setup/src/managed-skills.ts`), so every user has it. It holds
the primitives devstack composes: `orchestrate` (parallel workers with a completion envelope),
`page`, `automate`, `standup`, `setup`, `browser`.

The repo-local commands this work promotes live in `.agents/commands/`: `create-plan.md`
(ExecPlan template), `create-pr.md` (standards gate and PR body templates), `ci-check.md` (local
CI) and `respond-to-pr-comments.md`. They hardcode this repo's paths and commands.

No app, package or tRPC procedure changes. This work adds only plugin files, one marketplace
entry, the generated manifest bundle, and this repo's own `.devstack/config.md`.

## Decision Log

- Decision: devstack is a separate plugin, not more skills in the `superset` plugin.
  Rationale: the `superset` plugin is always-on and ships with the app; an opinionated workflow
  must be opt-in and version on its own tag so prompt changes do not need an app release. It also
  avoids name collisions with `orchestrate` and `standup`. devstack composes those skills by name
  instead of copying them.
  Date/Author: 2026-11-10, agent (recommendation; Harshith to confirm in review).

- Decision: skill folders drop the `dev-` prefix: `init`, `plan`, `fanout`, `review`, `qa`,
  `ship`, `watch`, `retro`.
  Rationale: installed skills are already namespaced by plugin (`devstack:plan`,
  `devstack-plan`), so `dev-plan` would install as `devstack-dev-plan`.
  Date/Author: 2026-11-10, agent.

- Decision: plugin name is `devstack`; skill text says "Paradev" for the product and `superset`
  for the CLI, and mentions the `paradev` alias once per skill.
  Rationale: matches `AGENTS.md` ("write `superset` in code and docs") and the existing skills.
  Date/Author: 2026-11-10, agent.

- Decision: per-repo configuration is `.devstack/config.md`: YAML frontmatter for values a skill
  reads (tracker, plans directory, checks, PR assignees and labels, roles, worker cap) and prose
  for repo conventions. `devstack:init` writes it.
  Rationale: one file that both agents and people read, committed with the repo so teammates
  without the plugin still see the conventions. It stays out of `.paradev/config.toml`, which the
  app parses.
  Date/Author: 2026-11-10, agent.

- Decision: the plan artifact is a markdown file `<plans_dir>/<YYYYMMDD-HHmm>-<slug>.md` with
  frontmatter (`devstack: plan/1`, `status`, `tracker`, `branch`), ExecPlan sections, and a
  `## Work units` section holding one fenced YAML block (`units: [{id, title, depends_on, owns,
  acceptance, verify, role}]`). `devstack:fanout` reads that block.
  Rationale: keeps the ExecPlan discipline from `create-plan.md`, and gives fan-out a
  machine-readable split with file ownership, which is the main control for merge conflicts.
  Date/Author: 2026-11-10, agent.

- Decision: workers end with the `SUPERSET_WORKER_DONE` / `SUPERSET_WORKER_BLOCKED` envelope from
  `superset:orchestrate`; reviewers end with a `DEVSTACK_REVIEW` envelope (verdict and findings).
  Rationale: reuse the existing protocol rather than a second one.
  Date/Author: 2026-11-10, agent.

- Decision: agents per role come from `roles` in `.devstack/config.md` (`coder`, `reviewer`). With
  no setting, the reviewer is a different terminal agent from `superset agents list` than the one
  that wrote the code; with only one agent, it is the same agent in a fresh workspace.
  Rationale: an independent review is the main thing a single terminal cannot give.
  Date/Author: 2026-11-10, agent.

- Decision: every skill works without the `superset` CLI. It checks `superset --help` once; with
  no CLI, fan-out runs the units in order in the current checkout and pages become markdown files
  in the plans directory.
  Rationale: the skills install into any agent on any machine; a hard failure would make the
  plugin useless outside Paradev terminals.
  Date/Author: 2026-11-10, agent.

- Decision: Linear first, GitHub Issues as fallback, `none` allowed (`tracker` in config).
  Rationale: Linear is the team's tracker and has a plugin; GitHub Issues is what most outside
  repos use.
  Date/Author: 2026-11-10, agent.

- Decision: `devstack:ship` never merges. It stops at a green, reviewed PR.
  Rationale: merge authority stays with a person; this matches `create-pr.md`.
  Date/Author: 2026-11-10, agent.

- Decision: the repo-local commands stay as they are for now.
  Rationale: teammates use them today. Once devstack is released and dogfooded, a follow-up can
  make them point at the devstack skills.
  Date/Author: 2026-11-10, agent.

## Plan of Work

Scaffold `plugins/devstack/` with `superset plugins create devstack --kind none`, then replace
the scaffolded manifest values (schema URL, author, homepage, icon) and remove the starter skill.
Add `assets/icon.svg`.

Write three skills, each generic and driven by `.devstack/config.md`:

`skills/init/SKILL.md` finds the repo's tracker, base branch, plans directory and check commands,
writes `.devstack/config.md`, and checks that the CLI and the needed plugins are present.

`skills/plan/SKILL.md` is `create-plan.md` without this repo's paths and stack: discovery,
questions, the plan skeleton, the Work units block, an approval gate, and the plan lifecycle
(`done/`, `abandoned/`).

`skills/ship/SKILL.md` merges `ci-check.md`, `create-pr.md` and `respond-to-pr-comments.md`:
run the configured checks, a standards gate against `AGENTS.md`, branch, commit, push, a PR body
scaled to the change, assignees and labels from config, wait for CI, triage failures, then
address review findings. It never merges.

Add a `devstack` entry to `PLUGIN_CATALOG` in `packages/shared/src/plugins/index.ts`; a test in
`packages/shared/src/plugins/index.test.ts` requires one for every published manifest.

Write `.devstack/config.md` for this repo, which is what `devstack:init` would produce here.
Publish with `superset plugins publish devstack`, which adds the marketplace entry and
regenerates the manifest bundle.

## Validation and Acceptance

    superset plugins validate plugins/devstack   # no problems
    bun run check:plugins                        # All plugins are valid and published.

Install from the working tree and confirm the skills appear:

    superset plugins marketplace add /workspace
    superset plugins install devstack
    superset skills list    # devstack-init, devstack-plan, devstack-ship

Then, in a fresh agent session in this repo, ask "use devstack:plan to plan <small change>" and
check that the plan lands in `plans/` with frontmatter and a Work units block that parses as YAML.

## Idempotence and Recovery

`superset plugins publish` is safe to re-run; it rewrites the same entry. Installing from a path
marketplace copies into a cache, so after an edit run `superset plugins install devstack --update`.
To remove a local test install: `superset plugins uninstall devstack`.

## Surprises & Discoveries

- Observation: the `superset` plugin is not in `.agent-marketplace.json`; it is a managed source
  bundled with the app.
  Evidence: `packages/agent-setup/src/managed-skills.ts`, `jq '.plugins[].name' .agent-marketplace.json`.
- Observation: no first-party marketplace plugin is skills-only yet, but publish allows it; it
  only rejects a plugin with neither skills nor an MCP server.
  Evidence: `checkPlugin` in `packages/cli/src/lib/plugins/publish.ts`.
- Observation: `superset plugins create` writes a `$schema` that points at the dev server
  (`http://localhost:3002/...`) and an `icon` key that is not a built-in icon.
  Evidence: scaffold output on CLI v2.0.8.

- Observation: `plugins install` and `marketplace add` are not available in a cloud sandbox, so a
  real install cannot be tested from one.
  Evidence: the commands are `sandbox: false`; see `docs/cloud-sandbox-mismatches.md`.
- Observation: a published manifest also needs a `PLUGIN_CATALOG` entry.
  Evidence: `packages/shared/src/plugins/index.test.ts` fails without it.
