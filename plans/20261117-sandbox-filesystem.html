Cloud sandbox filesystem: what lives where

The proposed layout for a cloud workspace box with a drive alongside it. Nothing a user does stops persisting: the root disk keeps its snapshot exactly as today, and the large, fast-changing data moves to a drive that is not part of that snapshot. The agents drive is merged behind a flag that is off. The workspace drive is a design, not built.

/workspace with one repo or several

This does not change. One repository is the workspace root itself. Several repositories each sit in a directory under it, named after the repo, with the owner added only when two names clash. Either way all of /workspace is one directory on the drive, so every checkout, and the shared package store beside them, lives on the same filesystem.

Why each thing is where it is

  • Restore time follows what was ever written to the root disk. A snapshot is a full block-level copy and deleting a file does not shrink it. So the root disk should be written rarely after the golden is made.
  • A drive is read on demand, not restored. Cold git status on a 5 GB checkout took 1.0 s; reading all 213k files of node_modules took 5 s. So large data costs nothing at wake.
  • The package store sits inside /workspace. Hardlinks fail across bind mounts even on one filesystem. Outside it, bun would copy 5 GB instead of linking.
  • Swap goes to the drive. A typecheck of this repo on an 8 GB box grows swap to 12 GB. On the root disk that is 12 GB in every later snapshot. A drive is not snapshotted.
  • Agents are read-only and shared. One copy per release for every box, so an agent update writes nothing to any workspace. Cold first launch is about one second.
  • Small identity files stay on the root disk. The control plane writes them before the drive layout exists, and they are tiny.

There is no rule for users to learn. The only thing that changes is which storage holds the bytes.

Open before this is built

  • Drive fork. A workspace's drive is forked from its environment's golden drive. Fork speed and cost have not been measured: no tool available to this work can call it.
  • Docker's data directory. Moving /var/lib/docker to the drive keeps image pulls off the root disk. Not tested on a drive.
  • Environment builds (#9282). A build would fork the golden drive, install onto it, and also snapshot the box, since [install] may change the system. History and restore then keep a box and a drive as a pair.
  • Drive billing after deletes. Drives have no discard either. Whether a drive's billed size shrinks when files are deleted is unknown.
  • Existing workspaces. The proposal is not to migrate them: they keep today's layout until archived.
