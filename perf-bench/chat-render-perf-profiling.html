Desktop chat rendering: production profile per commit

Follow-up to the suspect-commit list. I built the chat renderer in production mode at five commits, streamed the same long chat into each build in headless Chrome, and measured React commits, render time, long tasks and dropped frames. Result: #9339 (cloud chat history sync) is the regression, and only in cloud workspaces. #9582 (React Compiler + Vite 8) makes production rendering faster, not slower. A small change to SessionView fixes the regression. I did not open a PR.

Before the compiler (C), a throttled cloud chat spent 26 s of a 37 s run in long tasks and dropped almost every frame. Part of what canary users felt as "slower" may be cloud chats in general. The compiler brought that down, but the cloud cost from #9339 is still there at HEAD: about twice the local cost, with 82 frames over 33 ms.

Why: the stored history defeats the timeline memo

A text delta only changes snapshot.liveStreams. items and turns keep their identity, so useTimeline, useChildrenByParent and everything after them normally skip the work. In a cloud workspace, useStoredChatSnapshot keeps returning the stored chat after the box connects. Then withStoredHistory(storedSnapshot, session.snapshot) runs on every snapshot change and returns new items and turns Maps each time, even when nothing durable changed. So each animation frame re-derives the whole chat:

  • deriveTimeline, deriveChildrenByParent, railMessages, promptHistory and editableMessageIds over all 1,662 items: session component self time 12 → 204 ms.
  • transcriptRows + replyFooters and the row-keyed effects in Transcript: self time 70 → 378 ms.
  • editableMessageIds returns a new Set, so the ChatPaneActions context value changes on every frame. Every mounted ChatInlineCode, UserMessageRow and TurnChangesCard re-renders: about 9,200 + 600 + 600 extra renders over 150 updates.

A finished chat that a cloud box serves in full hits this case every time: the live chat starts at the stored chat's first item, so the merge always rebuilds the Maps.

Proposed fix

Merge again only when the live items, turns, cursor or session change, and take liveStreams from the live snapshot each render. Text deltas then keep the merged Maps, and every memo downstream holds. withStoredHistory itself does not change. 

// SessionView/hooks/useStoredHistory/useStoredHistory.ts
export function useStoredHistory(
	stored: SessionSnapshot | null | undefined,
	live: SessionSnapshot,
): SessionSnapshot {
	const { items, turns, cursor, session } = live;
	const merged = useMemo(
		() =>
			stored
				? withStoredHistory(stored, { ...emptySnapshot(), items, turns, cursor, session })
				: null,
		[stored, items, turns, cursor, session],
	);
	return useMemo(() => {
		if (!merged || merged.items === items) return live;
		return { ...merged, liveStreams: live.liveStreams, pendingReset: live.pendingReset };
	}, [merged, items, live]);
}

// SessionView.tsx
-	const shownSnapshot = useMemo(
-		() =>
-			storedSnapshot
-				? withStoredHistory(storedSnapshot, session.snapshot)
-				: session.snapshot,
-		[storedSnapshot, session.snapshot],
-	);
+	const shownSnapshot = useStoredHistory(storedSnapshot, session.snapshot);

Equivalence: in the bench I ran the fixed hook next to the current code for 154 renders: seed, the "host sent nothing yet" branch, durable item and turn events, and 150 deltas. items, turns, liveStreams and session matched entry for entry each time, with 0 mismatches. One small difference: before the host sends anything, the result now carries the live pendingReset and liveStreams instead of the stored ones. Nothing in the chat UI reads those two fields from the shown snapshot.

Effect: cloud drops to local cost at both B (12.5 → 6.8 ms/update) and HEAD (8.3 → 4.5 ms/update), and the throttled run goes from 82 to 4 frames over 33 ms. If the fix lands, add a test that streams a delta and checks that shownSnapshot.items keeps its identity.

Optional extra hardening: editableMessageIds could go through useStableList/a stable Set, so a real durable event does not re-render every ChatInlineCode through the context either. That is not needed to close this regression.

Other findings

  • #9582 is clean in production. Render time is −34% (local 6.9 → 4.6, cloud 13.0 → 8.5 ms/update), script time −37%, and throttled long tasks go from 55 to 1 (local). Vite 8 builds of this entry also take half the time (27 s vs 55 s).
  • About 6.5 React commits per streaming update, at every commit. Most come from an anonymous library component plus usePacedText's per-frame reveal. They are cheap (mean 0.7 ms), not a regression, and a possible follow-up. Cloud runs before the fix show fewer commits per update (4.0) only because heavy frames absorb the small ones.
  • No long tasks without throttling on any commit. The sandbox is faster than a typical laptop, so read the throttled table for what users feel.

Method and limits

  • Commits: A b7e21ed0 (before #9339) · B 361ee967 (#9339) · C bdd0a5be (before #9582) · D 71e664ff (#9582) · E 963279d1 (HEAD of this branch). One git worktree per commit, each with its own bun install.
  • Build: each commit's own electron.vite.config.ts renderer config (its plugins, Babel/compiler, Tailwind), with vite build in production mode. Only the entry changes, and react-dom/client is aliased to react-dom/profiling so <Profiler> reports. The compiler output is in D and E only (134 memo_cache_sentinel sites vs 0).
  • Harness: real useChatSession with a fake SessionClient (outline seed + delta envelopes), SessionView's streaming derivations, and the real Transcript with its providers. Cloud mode passes the stored snapshot the way useStoredChatSnapshot does.
  • Not measured: the composer, header, sidebar and the rest of the Electron app; Electron's own Chromium (this used headless Chrome 157); a real cloud box. Below #9623, TurnChangesCard's workspace.get query fails at once against an unreachable local port (once per card, not per update).
  • Harness and raw results live in perf-bench/ in workspace canary-chat-perf-profiling (not committed).
