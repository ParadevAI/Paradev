Desktop speed changes: chat streaming and workspace switching

Every change made to speed up the desktop app, what it does, and what it measured. Two problems: chat streaming in cloud workspaces, and switching between workspaces that have chat panes open. All numbers come from production builds of the renderer, not the dev build (dev mode was about 10× slower and misleading). Follow-up to the per-commit chat profile.

1. Chat streaming in cloud workspaces

Cause: in a cloud workspace, SessionView merges the chat stored in the database with the live one through withStoredHistory. It ran on every snapshot change and returned new items and turns Maps each time, even when a streamed delta only changed the live text. So every animation frame rebuilt the whole timeline, every transcript row, and a context that re-rendered every inline code span in the chat. Introduced by #9339.

Stable editable-message set SessionView.tsx editableMessageIds goes through useStableList, so the ChatPaneActions context keeps its value unless the set really changes. Stops a durable event from re-rendering every ChatInlineCode, UserMessageRow and TurnChangesCard. kept

2. Switching workspaces with chat panes open

Cause: not the chat transcript, which is cheap to show. On each switch, the panes' setup code (terminal, browser pane, tab bar, sidebar row, activity panel, overflow fades) read layout right after the page changed. Each read forced the browser to lay out the whole page again: about 7 times per switch at 20–35 ms each. Separately, every row in the Changes list and every diff header ran its own live query for the user's click settings.

4. What is still slow

A switch with chat panes is still about 420 ms on an 8-core sandbox, likely more on a laptop. From the production CPU profile of one switch:

  • Terminal rich-input editor (ProseMirror, TerminalRichInput): about 70 ms per switch in updateStateInner and attribute patching, even when it isn't open.
  • xterm focus(): about 25–30 ms, because focusing forces a style and layout pass.
  • Whole-page style recalculation: about 7 passes of 1,400–1,600 elements each; part of it is the body:has rule above.
  • React commit work for the rebuilt workspace subtree: every switch still remounts the whole pane tree (remountDeps on the route plus keyed providers).

Next candidates: mount the rich-input editor only when it is opened, and replace the body:has rule with a class set by the menu/dialog components.

How it was measured

  • Chat streaming: each commit's own production renderer build, with a harness mounting the real useChatSession (fake client), SessionView's streaming derivations and the real Transcript, in headless Chrome. React Profiler for render time; long tasks, long animation frames and dropped frames from Chrome.
  • Workspace switching: the full desktop app built with electron-vite build in production mode, driven with real clicks over CDP. First paint is two animation frames after the URL changes; long tasks and long animation frames come from PerformanceObserver; CPU profiles mapped to source through the build's source maps.
  • Benchmark scripts are in perf-bench/ in this workspace (part of the WIP commit; they should not ship in a PR).
