## Overview

A workspace lives on the machine that hosts its files, terminal, and ports. **Remote access** lets you reach a workspace hosted on another machine, such as a Mac mini, a shared sandbox, or a spare laptop.

**Paradev Relay** routes traffic between your devices. You can grant a device remote access through the relay in two ways:

## Option 1: Desktop

<Callout type="warn">
Exposing your primary workstation through the relay makes everything your local host service reaches (files, terminals, agent runs) reachable by clients you grant access to. Prefer a **separate machine** with only the repos and credentials you intend to share, so a misclick or compromised client can't touch unrelated projects or secrets.

Use the desktop toggle only when you need it on this machine. Otherwise use the CLI on a dedicated host.
</Callout>

Open the desktop app and go to **Settings → Remote Access**. Flip on **Allow remote access to this device via relay**.

![Settings → Remote Access relay toggle](/images/remote-workspaces-security-toggle.png)

Enabling the toggle restarts the host service and interrupts running terminals on this device. You must type a confirmation phrase first.

## Option 2: CLI

<Callout type="info">
See the CLI's [Getting Started](/cli/getting-started) and [Host Server](/cli/host-server) docs to get set up.
</Callout>

On the machine to add, sign in and start the host server.

```bash
superset auth login
superset start --daemon
```

`superset start --daemon` runs the host server in the background and registers the machine with the relay so other clients in your organization can find it.

Check that it is online:

```bash
superset status
```

### Headless (sandbox, CI, or server)

On a machine with no browser to complete an interactive login, authenticate with an API key instead. Create one in **Settings → API Keys**, then export it. The CLI reads `SUPERSET_API_KEY` automatically (no `superset auth login` needed):

```bash
export SUPERSET_API_KEY=sk_live_…
superset start --daemon --org <id|slug|name>
```

`--org` picks the organization the host registers under. It is required when your key belongs to more than one organization; with one, you can omit it. The host claims itself to the key's user on first registration. No desktop step is needed.

Every `hosts` and `status` command takes the same `--org`:

```bash
superset hosts list --org <id|slug|name>
superset status --org <id|slug|name>
```

## Set Up a Host Over SSH

In the desktop app, open **Settings → Hosts** and choose **Set up a host over SSH**. Enter the SSH destination (`user@box` or a Host alias). The dialog runs [`superset hosts add`](/cli/cli-reference) in an embedded terminal, so password, host-key, and install prompts work as in any terminal. When it finishes, the new host appears in the list. If it fails, edit the destination and retry.

## Connect from an iPhone or iPad

Install [Paradev for iPhone and iPad](/install#iphone-and-ipad) and check its requirements before connecting. You can use [cloud workspaces](/cloud-workspaces) without connecting your own computer.

To connect to workspaces hosted on your own computer:

1. On your computer, enable **Allow remote access to this device via relay** in **Settings → Remote Access**. You can also use the inline toggle in **Settings → Mobile** when that tab is available. Both toggles control the same setting.
2. On your iPhone or iPad, sign in with the same Paradev account and select the same organization. The QR code in desktop Mobile settings opens the App Store; it does not sign you in.
3. Select your computer and open a workspace to continue its terminal sessions, send prompts, review diffs, or merge PRs. Keep the computer awake, online, and running Paradev.

If your computer does not appear online, see [Remote Host Won’t Connect](/troubleshooting#remote-host-wont-connect).

## Grant teammates access

When a host first comes online, the user who started it is the only one with access. Other members of your organization won't see it in their workspaces list until you add them.

Open **Settings → Hosts** in the desktop app, pick the host, and use **Add member** to grant teammates access. Owners can promote members to owner or remove them from the host.

![Settings → Hosts members table](/images/remote-workspaces-hosts-members.png)

## Reach a remote host from another device

On any other device signed into the same organization, open the desktop app's **Workspaces** list. Use the **Device** filter in the top right to pick a remote host:

- **This device**: workspaces on the machine you're using now
- **Other devices**: each remote host that has opted in, listed by name with an online indicator

![Device filter in the workspaces list](/images/remote-workspaces-device-filter.png)

Pick a remote host to see the workspaces hosted there. Terminals, agent runs, and the diff viewer all work, proxied through the relay to the host.

### Ports on a remote host

The ports sidebar shows ports listening **on the remote host**. When you select a remote workspace, the desktop app forwards each of its ports to the same port number on your machine, so `localhost:3000` reaches the dev server on the host. All traffic for a workspace shares one tunnel, opened when you select it. Selecting another workspace stops those forwards and starts forwards for the new workspace.

Only ports that the workspace started are forwarded. Other services on the host stay unreachable.

If a local process already uses the port, the row shows **local port busy** and offers two actions: stop the local process (only when a Paradev workspace started it) or **Use another port**, which maps the remote port to a free local port and shows the mapping, for example `3000 → localhost:54321`.

The remote server sees each forwarded connection as coming from its own loopback address; there is no real client IP. Only TCP is carried; anything UDP (WebRTC media, mDNS) does not ride the forward.

Forwarding needs a host on the current relay running host-service 1.26 or newer. For a host you reach some other way, [forward a port yourself](/ports#forward-a-port-yourself) with SSH or Tailscale.

Forwarded traffic passes through the Paradev relay, like terminal traffic does. A browser sends its usual cookies, auth headers, and query strings to a forwarded dev server, so treat a forwarded port as the remote service, not as localhost.

## Turning access off

- **Desktop**: flip the toggle in **Settings → Remote Access** back off. The host service restarts and stops accepting relay traffic.
- **CLI**: run `superset stop` on the host machine.

In both cases, in-flight terminals and host-backed work on that machine are interrupted.
